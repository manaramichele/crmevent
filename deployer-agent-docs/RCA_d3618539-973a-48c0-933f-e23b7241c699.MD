# RCA — "Trento" org shows Pisa (TriO) people in Staff/Volontari

DB: `manage-events-12-test_database` (prod). Read-only. No data changed.

## Problem statement
Super Admin selects org "A.S.D. Città di Trento" in the "Org attiva" selector (sets `acting_org_id` / `X-Org-Id`). `GET /api/persons-enriched` then returns people linked to event "Maratona di Pisa", which belongs to another org. Question: were the Pisa records saved with Trento's org_id (data issue), or is scoping correct and only the display wrong?

## Answer (short)
Neither of the two options as framed. **There is NO organization "A.S.D. Città di Trento" in the database**, and the Pisa records in question were **NOT** saved with any Trento org_id — they have **no org_id at all (null/missing)**. Real-org scoping (e.g. TriO) is correct. The leak happens because selecting a non-existent org resolves the active org to null, and the persons-enriched query then matches all orphaned null-org records.

## Evidence

### 1. Orgs (6 total) — no Trento
`organizations` has exactly 6 docs; none contain "Trento"/"Città":
- `312f9c27220d4a8eafe354dc12398f1e` = TriO Events
- `036cc51a7e24444bb56e54b6cbb69d40` = Demo
- `1ab0359e20334753ad1fc1b9488fa6b4` = Personalizzandia Snc
- `42ef277ddbab4019940a42f25ee4f1ea` = MASSIMO GHEZZI
- `a333f237f05e49ff922666c7a5983315` = Total Training
- `40c7a02fd95d4db4ab660bad5319ebd2` = ASD ATLETICA PODISTICA SAN GAVINO

Regex `/trento|citt/i` on nome/name → 0 hits. No Trento in `users` or `memberships` either.

### 2. Pisa events — two, one orphaned
`events` matching `/pisa/i` → 2:
- `d15ceccb5473445a81f0dcb2874b1720` "Maratona di Pisa", **org_id = TriO** (legitimate, TriO-owned).
- `1d5ee9b82eb942beb6534210cbfe0d8e` "Maratona di Pisa", **org_id = MISSING (null)**, organizzatore="TriO Events", created_at 2026-09-23. This is the orphaned event the Super Admin is seeing.

No Pisa event has org_id = any Trento id (no Trento id exists). → **Q2 = No.**

### 3. Orphaned (null org_id) records — the data that leaks
- `events` org_id=null → **1** (the orphaned Maratona di Pisa above).
- `staff` org_id=null → **6**. One of them (`52004aa937bf4a7f906fc54e4cd482bf`) has evento_id = the orphaned Pisa event and persona_id `179c08288898479388faffb4ec6ffc03`.
- `persons` org_id=null → **14** (all 14 have no provenienza/created_by fields at all → cannot be attributed to a Super-Admin creation event; look like legacy pre-org-scoping data).

Super-Admin-created attribution (Q4): `persons` with org_id=null AND provenienza present → **0**. So these orphans predate org scoping rather than being freshly created under Trento.

### 4. Super Admin selected phantom/deleted orgs — the trigger (Q5)
`audit_logs` action="org_access" includes two org_ids that do NOT exist in `organizations`:
- `47c80a2596be488e93c17a2bd32b04e8` — accessed 2026-10-03T13:21:19Z
- `97a0a2f15d354f5b8e68dc046c3e55f9` — accessed 2026-09-26T16:33:44Z

Both confirmed absent from `organizations` (lookup by id → 0). This proves the selector lets a Super Admin pick an org id that has no matching organization doc (deleted/phantom) — almost certainly how "A.S.D. Città di Trento" was selected. (Only action "org_access" exists; no "platform_org_access" variant found.)

### 5. TriO cross-org check (Q6) — scoping is correct for real orgs
- TriO owns 2 events: `d15ceccb...` (Maratona di Pisa) and `ae0253a6...` (Trail Delle Streghe).
- `staff` where org_id=TriO → all reference evento_id `d15ceccb...` only (distinct evento_id = exactly that one, a TriO event). No TriO staff points at another org's event.
- `persons` org_id=TriO = 102. TriO scoping is clean — no leakage into/out of TriO.
- Q2/Q3 restated for Trento: there is no Trento org_id, so there are 0 staff with org_id=Trento (the implicated staff carry null, not Trento). The "cross-org staff" the customer suspected is really null-org staff.

## Root cause
Two compounding issues:

1. **CODE / scoping (primary leak mechanism):** `_resolve_active_org` resolves a selected org id that has no matching `organizations` doc (phantom/deleted, e.g. the "Trento" entry) to a null/None org_id instead of rejecting it. `persons-enriched` then queries `{org_id: None}`, which matches every orphaned null-org record — the orphaned "Maratona di Pisa" event, its 6 staff and 14 persons. That is exactly the "Pisa people under Trento" the customer sees. The per-collection org_id filters are present and work for real orgs; they just don't guard against an unresolved/empty active org (null matches null).

2. **DATA (the records that leak):** 1 event + 6 staff + 14 persons have null/missing org_id (orphans, created ~2026-09-23, no provenienza) and are never attached to any org. These are what surface whenever the active org resolves to null.

Not supported by evidence: the Pisa records were NOT saved with a Trento org_id, and there is no Trento organization. So "data saved under Trento" is false; "scoping correct, pure display bug" is also not accurate — the backend genuinely returns these rows because of the null active-org fallback.

## Suggested fixes
- **Code (E1):** In `_resolve_active_org`, when the X-Org-Id/acting_org_id does not resolve to an existing organization the Super Admin may act on, do NOT fall back to None. Return 400/403 or an empty scope — never build a `{org_id: None}` query. Also make the "Org attiva" selector list only existing organizations so deleted/phantom ids (e.g. `47c80a25...`, `97a0a2f1...`) can't be selected. Harden persons/staff/teams/events queries to treat a null active org as "no results" rather than "all null-org rows".
- **Data (User, via DB Manager — do not auto-run):** Decide the correct owner for the 1 orphaned event (`1d5ee9b8...`, organizzatore "TriO Events" → likely TriO `312f9c27...`), its 6 null-org staff and 14 null-org persons, and backfill org_id accordingly (or quarantine/delete if they are junk). Until backfilled, these remain exposed to any null-active-org scope.
