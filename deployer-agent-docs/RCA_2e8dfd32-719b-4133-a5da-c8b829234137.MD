## Failure stage (pinpointed)
- Before redirect to Google: OK.
- Google consent: OK (Google returned a code + granted scope).
- Callback reached backend: OK.
- **code -> token exchange at https://oauth2.googleapis.com/token: FAILS** — Google returns an error JSON with no access_token. <-- THIS IS THE FAILING STAGE.
- Token save: never reached.

## 5. Scopes actually requested
`SCOPES = ["https://www.googleapis.com/auth/calendar"]` (gcal_utils.py:13). Google's redirect back carried `scope=https://www.googleapis.com/auth/calendar` — exactly the single full calendar scope. No scope mismatch, no invalid_scope, no consent re-prompt loop.

## 6. Which misconfiguration is this consistent with
Because the **authorize step succeeded** (Google displayed consent and redirected back to our redirect_uri with a valid code), the following are RULED OUT:
- redirect_uri NOT authorized in the OAuth client — RULED OUT (authorize validated & used exactly `https://crmevent.it/api/oauth/calendar/callback`).
- unauthorized scope / invalid_scope — RULED OUT (scope granted).
- Google app in Testing mode / user not a Test User / app not published / org_internal — RULED OUT (these block BEFORE the redirect back; the user got a code).
- unauthorized domain — RULED OUT (consent completed).
- network failure to Google — RULED OUT (307 not 500; Google returned a JSON error).

REMAINING, MOST PROBABLE cause (INFERRED, not directly observed — the app swallows Google's error body):
- **`invalid_client`** at the token endpoint = **GOOGLE_CLIENT_SECRET does not match GOOGLE_CLIENT_ID** (wrong secret, secret from a different OAuth client, or a rotated/stale secret in the deployment). Token exchange is the FIRST step that uses the client_secret; authorize only needs the (public) client_id, which is why authorize can succeed while token fails. This best fits "authorize OK + token returns error JSON with no access_token + connection never once saved."
- Less-likely alternative: `invalid_grant` (code expired/already used) — but that is transient and would not explain a permanent, never-succeeded state across multiple attempts.

## Fix — where it lives
- NOT a redirect_uri / publishing / test-user problem, so NO change needed to Authorized redirect URIs or the OAuth consent screen publish state.
- Primary fix is CONFIG (user side): re-set **GOOGLE_CLIENT_SECRET** in Deployment Panel -> Secrets so it exactly matches the OAuth client identified by GOOGLE_CLIENT_ID (copy the client secret for that same client from Google Cloud Console -> APIs & Services -> Credentials -> the OAuth 2.0 Client). Confirm GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET belong to the SAME "Web application" OAuth client. Then redeploy so the new secret is loaded, and retry Connect.
- Recommended CODE improvement (E1, optional, to make this self-diagnosing next time): in `calendar_callback`, log the Google token response on failure (redacting tokens), e.g. log `tokens.get("error")`/`error_description` before the error redirect, and wrap `exchange_code` in try/except. This would confirm invalid_client vs invalid_grant definitively.

## Confidence
- Definitively proven (tool evidence): failing stage = code->token exchange; Google returned an error JSON (307 not 500); connection never saved (collection absent); exact redirect_uri & scopes; env presence; URL values.
- Inferred (not directly observed, because the app does not log Google's error body and the single-use code cannot be replayed): the specific Google error is `invalid_client` due to a client_secret mismatch. Verifying/refreshing GOOGLE_CLIENT_SECRET is the highest-probability fix.
