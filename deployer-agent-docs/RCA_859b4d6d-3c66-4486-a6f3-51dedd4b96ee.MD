# RCA — crmevent.it: "Ricerca da Brevo" still reports Brave Search not configured

## Problem statement
Super Admin page "Calendario Eventi Italia > Ricerca da Brevo" shows
"Motore di ricerca non configurato: manca la chiave Brave Search."
Flag source: `GET /api/platform/cal/reverse/status` →
`"brave_configurato": bool(os.environ.get("BRAVE_API_KEY"))` in `backend/cal_reverse.py`.
User saved BRAVE_API_KEY via the secure secrets card (updated 2026-11-07T13:20Z) and redeployed.

## What I verified (all deployment-side links are CORRECT)

1. **Secret exists & is non-empty in production.** `list_secrets` on the ACTIVE run
   `859b4d6d-3c66-4486-a6f3-51dedd4b96ee` lists `BRAVE_API_KEY` with `is_empty:false`,
   `metadata_available:true`. The run's secret rows ARE the env injected into the pod, so the
   running backend's OS env contains a non-blank BRAVE_API_KEY. (Value never read/printed.)

2. **The post-save run is the one serving.** Active run `859b4d6d` was created 13:26:44Z —
   after the 13:20Z secret save; its `manage_secrets` step ran 13:31:24Z. All steps success
   (build → mongodb_migrate → manage_secrets → deploy → health_check). Both replicas Running,
   ready=true, restart_count=0, on image `...:859b4d6d...`, started 13:31:25Z. (Transient 503
   startup-probe blips during boot, then ready.) Promote succeeded (active_run_id = this run).

3. **The build includes `backend/cal_reverse.py` and the route is served.** Live probe of
   `/api/platform/cal/reverse/status` returns HTTP **401** `{"detail":"Non autenticato"}` —
   the route exists and is super-admin gated (a missing file would be 404).

4. **No baked `.env` is shadowing the key.** Source inspection (eph pod, run 859b4d6d):
   - `backend/cal_reverse.py` status handler reads `os.environ.get("BRAVE_API_KEY")` fresh on
     every request (not cached at import).
   - `backend/server.py` line 4: `load_dotenv(ROOT_DIR / '.env')` → default `override=False`,
     so the injected OS env wins over any file value.
   - The baked `backend/.env` key list does NOT contain BRAVE_API_KEY at all, so there is no
     empty/stale file value to override anything.

Conclusion: on the currently-serving revision, `os.environ.get("BRAVE_API_KEY")` resolves to a
non-empty value, so `/status` should return `brave_configurato=true`.

## Could NOT directly observe
The `/status` body is super-admin auth-gated and there is no exec into the production pod, so I
could not read the live `brave_configurato` boolean or dump the pod env directly. The conclusion
above is inferred from: secret-store contents of the active run (= injected env, by platform
design) + source code + pod/revision state. That chain is sound but the final live boolean is
inferred, not directly observed.

## Root cause
Not a deployment/secret-injection fault. The key is present, non-empty, and injected into the
live revision, and the code reads it correctly — so the backend should already report it
configured. The persistent "not configured" message is almost certainly a STALE CLIENT view:
the Super Admin browser (or edge) is serving a cached JS bundle / cached `/status` response from
before the 13:32Z deploy completed.

## Recommended fix
1. (User) Hard-refresh / open the Super Admin page in a private window to drop the cached bundle
   and `/status` response, then re-open "Ricerca da Brevo". Confirm the banner clears and
   `/api/platform/cal/reverse/status` returns `brave_configurato:true`.
2. (Only if it STILL shows missing after a clean hard-refresh) escalate to Emergent support as a
   secret-injection anomaly: the deployment secret store shows BRAVE_API_KEY non-empty on the
   active run, so a live pod reporting it absent would be a platform injection discrepancy worth
   a direct pod-env check. No code or redeploy change is warranted first.

No deployment action taken (diagnosis only).
