## How the UI message is produced (frontend `components/calendario/ReversePanel.jsx`)
There are TWO distinct "Brave" messages:
- Line 124 banner: `!st.brave_configurato && "Motore di ricerca non configurato: manca la chiave Brave Search."` — gated on `brave_configurato` (currently **true**), and its wording does NOT contain the token `BRAVE_API_KEY`. So this is not what the user sees.
- Line 56 (JobBar): `{(job.motivo || job.ultimo_errore) && <p>{job.motivo || ...}</p>}`, where `job` (line 115) = `st.jobs.find(j => ["running","sospeso"].includes(j.status))`. The suspended-job motivo text is exactly `Chiave Brave Search mancante (BRAVE_API_KEY)` (set at `cal_reverse.py:178/395`) — this is the literal `BRAVE_API_KEY` string the user reports. **The user's hypothesis about WHICH element is correct: it's the JobBar `job.motivo`, not the brave_configurato banner.**

Critically: `job` is derived only from `st.jobs`, and `st` is only ever set from a **successful** `/reverse/status` 200 (`load()`: `setSt(data)` on success; on error it calls `err` and does NOT touch `st`). On a fresh mount `st` is null → the panel shows "Caricamento...". So a 401 cannot produce the JobBar; only a 200 response that actually contains a running/sospeso job can.

## Root cause
The live backend and production database are **clean**: BRAVE_API_KEY is configured (`brave_configurato=true`), and there is **no suspended job and no missing-key data anywhere in the production DB** (no `cal_rv_jobs`/`cal_settings`, empty `cal_rv_contacts`). A correct fresh load of `/reverse/status` for this deployment returns `jobs: []`, so the JobBar (and therefore the `...(BRAVE_API_KEY)` motivo) must NOT render.

Therefore the "BRAVE_API_KEY missing" the user still sees is **stale client/edge state, not current backend state**: the JobBar is rendering an old suspended-test-job's `motivo` from a cached `/reverse/status` response captured before the key was added (when such a job briefly existed), served from the browser HTTP cache or the Cloudflare edge/worker on the `/api` path — which a plain hard refresh is not busting. (Equivalent surface-level cause: a stale browser tab / non-production surface still holding that old response.)

Confidence: backend-key state, pod timing, DB contents, logs, and frontend render logic are all directly verified via tools. The caching mechanism itself is inferred (I could not read the live Cloudflare worker / response Cache-Control headers), but it is the only path consistent with a clean DB + clean backend still showing the old motivo.

## Suggested fixes
1. **User (verify / cache):** Clear site data for crmevent.it (or open in a fresh incognito window / different browser) and reload "Ricerca da Brevo". The JobBar and the `(BRAVE_API_KEY)` motivo should disappear, and `brave_configurato` is true. If the app is fronted by Cloudflare cache rules on `/api/...`, purge the cache for `/api/platform/cal/reverse/status`. This alone should resolve the reported symptom.
2. **Code (E1), hardening to prevent recurrence:** Set `Cache-Control: no-store` on the `/api/platform/cal/reverse` GET responses (especially `/reverse/status`) so neither the browser nor the Cloudflare edge can serve a stale snapshot. Optionally: since a suspended job's motivo persists until acted on, consider having `/reverse/status` recompute/clear the `BRAVE_API_KEY` motivo when `brave_configurato` is true (or auto-resume/clear such suspended jobs once the key is present) so a genuine stale DB job can't surface an obsolete message.
