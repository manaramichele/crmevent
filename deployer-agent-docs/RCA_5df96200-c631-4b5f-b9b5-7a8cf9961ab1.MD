# RCA — Google Calendar OAuth failing in production (crmevent.it)

**Deployment:** manage-events-12 (`e3597518-...`)  
**Active run:** `5df96200-c631-4b5f-b9b5-7a8cf9961ab1` (type=secret_reuse, trigger=secret_change, completed 2026-09-25 13:05:55)  
**Frontend:** Cloudflare → k8s backend (2 pods: 24kdc, rbrbr)  
**Symptom:** clicking "Collega Google Calendar" → toast "Errore collegamento Google Calendar" (browser lands on `/app?calendar=error`).

## Verdict
The failure is **DURING the OAuth callback, at the Google token exchange step** (`gcal_utils.exchange_code`) — **NOT** before the redirect to Google. Config/secrets are correctly present and injected; Google's authorization step succeeds and returns a valid auth code, but the subsequent server-side token POST to `https://oauth2.googleapis.com/token` is **rejected by Google (no `access_token` returned)**, so the callback redirects to `?calendar=error`.

Most probable Google error: **`invalid_client`** — i.e. `GOOGLE_CLIENT_SECRET` does not correspond to `GOOGLE_CLIENT_ID` (wrong/mismatched/stale secret value, or secret copied from a different OAuth client). This is the one failure that passes the authorization step (which never sees the secret) yet fails only at token exchange.

## Evidence (production runtime + secret store)

**1. GET /api/calendar/connect** — returns **200 OK** in production (pod log 13:16:17 `GET /api/calendar/connect HTTP/1.1 200 OK`). It is NOT returning 400. `is_configured()` is therefore **True**. (An unauthenticated probe returns 401 `{"detail":"Non autenticato"}` — that is just the auth wall, not the OAuth fault.)

**2. Env vars seen by the running backend (list_secrets on the active run, metadata_available=true):**
- `GOOGLE_CLIENT_ID` — present, non-empty
- `GOOGLE_CLIENT_SECRET` — present, non-empty (value never revealed; correctness NOT verifiable from here)
- `BACKEND_PUBLIC_URL` — present, non-empty, **matches_expected=true** for `https://crmevent.it` → **no trailing slash / no whitespace**
- `APP_URL` — present, non-empty, **matches_expected=true** for `https://crmevent.it`

**3. Resolved redirect_uri** = `{BACKEND_PUBLIC_URL}/api/oauth/calendar/callback` = **`https://crmevent.it/api/oauth/calendar/callback`** (well-formed, single slash). Google **accepted** this URI — it issued an auth code back to it — so it IS registered byte-for-byte in the Google client.

**4. Callback attempts in production logs (pods 24kdc/rbrbr):** four attempts — 13:08:47, 13:10:00, 13:10:41, 13:16:25 — each:
```
GET /api/oauth/calendar/callback?state=<JWT>&iss=https://accounts.google.com&code=4/0AXlqoi...&scope=https://www.googleapis.com/auth/calendar HTTP/1.1  307 Temporary Redirect
```
The `307` is the `RedirectResponse({APP_URL}/app?calendar=error)`. Because the callback code has **no try/except around `exchange_code`**, a network/egress failure would surface as a **500**, not a 307 — so the 307 proves `exchange_code` **returned a dict without `access_token`**, i.e. Google explicitly returned an error JSON. Egress to Google works.

**5. Exact Google error string is NOT in the logs.** `gcal_utils.exchange_code` does `requests.post(...).json()` and the callback silently redirects when `"access_token" not in tokens` — the Google error body (`error`/`error_description`) is **never logged**. This is a code observability gap, not the root cause.

**6. Secrets ARE injected / revision is current.** The serving pods belong to run `5df96200`, which was triggered by the **secret change** and completed 13:05:55; that run's env shows `BACKEND_PUBLIC_URL` and `APP_URL` present with matches_expected=true, and `/api/calendar/connect` returns 200 → the new secrets are live in the running container. **No stale revision. A further redeploy is NOT needed to pick up the secrets.**

## Hypotheses assessed
- **(a) Stale revision / secrets not picked up — RULED OUT.** Active run is the secret-change run; secrets present & matching; connect=200.
- **(b) BACKEND_PUBLIC_URL trailing slash / malformed — RULED OUT.** matches_expected=true (exactly `https://crmevent.it`); resolved redirect_uri has a single slash; Google accepted it (code issued).
- **(c) Google consent in Testing / access_denied / redirect URI not registered — RULED OUT for this symptom.** User reached consent, consented, and Google redirected back **with a valid `code`** to `https://crmevent.it/api/oauth/calendar/callback`. No `access_denied`; redirect URI is registered.
- **(d) Scope mismatch (broad `.../auth/calendar` vs consent screen) — RULED OUT as the cause.** The callback URL returned `scope=https://www.googleapis.com/auth/calendar` — Google **granted** exactly the requested scope and issued a code. A scope not permitted would fail at authorization (`invalid_scope`) before any code; that did not happen.
- **(most likely) invalid_client at token exchange.** Authorization validates only client_id + redirect_uri (both good). The token POST additionally sends `client_secret`; a wrong/mismatched secret fails **only here**, producing exactly the observed "code issued, then token exchange returns no access_token → ?calendar=error" pattern. (Secondary possibility `invalid_grant` from code reuse/expiry is unlikely given it fails systematically on 4 fresh codes.)

## Fix required (apply, then verify)
1. **User → Google Cloud Console (third-party):** For the OAuth 2.0 **Web application** client whose ID is stored in `GOOGLE_CLIENT_ID`, regenerate/copy the **matching client secret** and re-save it in **Deployment Panel → Secrets → `GOOGLE_CLIENT_SECRET`** (no surrounding spaces/newline). Confirm the ID and secret come from the **same** client. Ensure the client's Authorized redirect URI list contains `https://crmevent.it/api/oauth/calendar/callback` (it already does, since auth succeeded). Save secret → redeploy so the corrected secret is injected, then retry the connect flow.
2. **Code → E1 (observability, not root cause):** In `gcal_utils.exchange_code` / the callback, log the Google token response body (`tokens.get("error")`, `error_description`) before redirecting to `?calendar=error`. This will surface `invalid_client` vs `invalid_grant` directly in future logs instead of a silent 307.

**Not verifiable from here:** the actual value of `GOOGLE_CLIENT_SECRET` (secret values are never returned) and Google's exact error string (app does not log it). The invalid_client conclusion is inferred from the flow: authorization succeeded with a code + full scope, token exchange rejected — the classic signature of a client_secret that doesn't match the client_id.
