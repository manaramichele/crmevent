## RCA — CRMEvent / Cloudflare "could not parse response" (Error 520) dopo redeploy HEAD f7d17c5

### Esito in breve
L'app NON è giù e NON è in crash-loop. Al momento della diagnosi backend e frontend sono **sani** e servono traffico correttamente. L'errore Cloudflare visto dall'utente è stato con ogni probabilità **transitorio, durante la finestra di rollout** dell'ultimo deploy. L'ipotesi "immagine stantia con `NameError: Body`" è **smentita dai log**.

### Stato verificato (run attivo c3958e20-8c37-4316-9f97-4a5bd09dc774, immagine sha256:89060e2d…)
- **Pod backend UP, nessun crash-loop.** Entrambi i pod (`...-ngfx9`, `...-s5t5m`) sono `Running`, `ready: true`, `restart_count: 0`.
- **Import di server.py pulito.** I log runtime mostrano l'avvio completato:
  - `Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001`
  - `INFO: Application startup complete.`
  - `INFO: Uvicorn running on http://0.0.0.0:8001`
  - `INFO:crmevent:Stripe inizializzato in modalità LIVE`, `INFO:crmevent:Storage initialized`
  - **Nessun** `NameError` / `ImportError` (nessun riferimento a `Body`). Nota: se `Body` fosse indefinito all'import, uvicorn non raggiungerebbe mai "Application startup complete" — quindi l'immagine in produzione contiene il codice corretto, non lo snapshot difettoso.
- **L'immagine in esecuzione serve richieste reali 2xx/4xx:** `GET /api/auth/me 200 OK`, `POST /api/cron/brevo-funnel-tick 200 OK`, `GET /api/auth/me 401 Unauthorized`.
- **Probe live attuali:** default URL `/` → 200 (HTML reale CRMEvent); `/api/auth/me` → 401 `{"detail":"Non autenticato"}` (backend vivo, solo gated); `/health` edge → 200.
- **Domini:** `crmevent.it` e `www.crmevent.it` → `verified: true`, `ssl_status: active`, DNS `linked: true`.
- **Build:** run c3958e20 `status: success`; nessuno step fallito.

### Causa del 520 Cloudflare (finestra di rollout)
Eventi/log del pod durante il deploy:
- Pod schedulati 12:31:34; **pull immagine da 776 MB** (~1m56s su un nodo).
- `Startup probe failed: HTTP probe failed with statuscode: 503` alle 12:31:54–12:32:04 (ngfx9) e 12:33:34–12:33:44 (s5t5m).
- nginx: `connect() failed (111: Connection refused) while connecting to upstream "http://127.0.0.1:8001/health"` — uvicorn non era ancora in ascolto.

Frontend Cloudflare (static da R2 + proxy `/api` → backend k8s): durante questi ~2–3 minuti di boot, le chiamate `/api` proxate all'origin ricevevano 503/risposta vuota → Cloudflare mostra "origin returned an empty response / could not parse". Terminato il boot (pod Ready, restart 0), il traffico scorre normalmente.

### Risposte alle domande RCA
- a) Pod backend: **UP**, non in crash-loop (restart_count 0, entrambi Ready).
- b) Log di startup: avvio **pulito**, nessun traceback / NameError su `Body`.
- c) Commit/immagine in esecuzione: immagine dell'ultimo run (sha256:89060e2d…), **build riuscita**, codice corretto (import ok).
- d) Portata: **nessun outage attuale** dell'intera app; il 520 era limitato alla finestra di rollout, non a un singolo endpoint di codice.
- e) Root cause: **errore Cloudflare transitorio durante il rollout**, non immagine stantia. **NON serve un redeploy "al buio"** per correggere un bug: il codice f7d17c5 è già in produzione e sano.

### Azioni consigliate
1. **Utente (test & verify):** fare hard refresh / riprovare su `crmevent.it`. L'errore dovrebbe essere già scomparso. Se dovesse ripresentarsi stabilmente (non solo durante un deploy), catturare la richiesta che fallisce in DevTools (URL, status, response headers) per una nuova analisi.
2. **Contesto (non bloccante):** il 520 compare prevedibilmente ad ogni deploy per alcune decine di secondi, perché l'immagine è grande (776 MB) e il boot su tier_0 (pull + avvio uvicorn + init Stripe/Storage) è relativamente lento rispetto alla finestra della startup probe. L'app resta sana a regime; questo è un artefatto della finestra di rollout, non un bug del codice.
